# Cwork

**ระบบบริหารทรัพยากรบุคคล (HRIS) แบบโอเพนซอร์ส — พนักงาน สรรหา การลา ลงเวลา

## ประกอบด้วยอะไรบ้าง

สามส่วนที่ติดตั้งแยกกัน ใช้ฐานข้อมูลเดียว:

| | |
|---|---|
| **เว็บคอนโซล** | React 19 + Vite สำหรับงาน HR เงินเดือน และหัวหน้างาน |
| **แอปพนักงาน** | Flutter ลงเวลา ขอลา ดูสลิป อนุมัติ — ใช้งานต่อได้แม้เน็ตหลุด |
| **API** | NestJS แบบ modular monolith บน PostgreSQL 16 |

ไม่มี Redis ไม่มี message broker ไม่มี Kubernetes การรัน API หลาย instance ใช้
การตั้งค่าเพียงบรรทัดเดียว (`THROTTLE_STORAGE=postgres`) ไม่ใช่การเพิ่มบริการใหม่
ให้ต้องดูแล — ระบบ HR ที่ต้องมีคลัสเตอร์ Kafka เพื่อส่งแจ้งเตือนการลา คือระบบที่
ไม่มีใครติดตั้งใช้เองได้

**หนึ่ง deployment ต่อหนึ่งองค์กร** ทุกตารางมี `organizationId` และทุก query
กรองด้วยคอลัมน์นี้ แต่นั่นคือการป้องกันซ้อนชั้นภายใน deployment เดียว
ไม่ใช่เส้นแบ่งระหว่างองค์กร — ไม่มีเทสต์ตัวไหนครอบคลุมกรณีสององค์กรใช้
ฐานข้อมูลร่วมกัน จึงไม่ควรมีอะไรไปพึ่งพาสมมติฐานนั้น

## ลองใช้ภายในห้านาที

```bash
git clone https://github.com/SuruchBoss/Cwork.git
cd Cwork
cp .env.example .env
```

กรอกค่าลับที่ `.env` ขอไว้ — ถ้าไม่ครบ compose จะไม่ยอมสตาร์ท:

```bash
openssl rand -base64 48   # JWT_ACCESS_SECRET, JWT_REFRESH_SECRET
openssl rand -base64 32   # FIELD_ENCRYPTION_KEY
                          # และ POSTGRES_PASSWORD ตั้งเป็นอะไรก็ได้
```

จากนั้น:

```bash
docker compose up -d --build
docker compose run --rm --build migrate            # รัน migration
docker compose run --rm migrate npm run db:seed    # ข้อมูลตัวอย่าง — สำหรับทดลองเท่านั้น
```

เปิด **http://localhost:8080**

| | |
|---|---|
| **เข้าแบบพนักงาน** | `dev2@cwork.example` / `Cwork2026!` — ใช้รหัสผ่านอย่างเดียว |
| **เข้าแบบ HR** | `hr.manager@cwork.example` / `Cwork2026!` — **ต้องใส่รหัส 2FA ด้วย** |

บัญชีผู้ดูแลต้องใช้ปัจจัยที่สองจริง ๆ คำสั่ง `db:seed` จึงพิมพ์คีย์ TOTP
สำหรับสาธิตพร้อมลิงก์ QR ออกมาให้ เพิ่มเข้าแอป Authenticator ครั้งเดียว
ใช้ได้กับบัญชีผู้ดูแลทุกบัญชี

> **migration รันผ่านเซอร์วิส `migrate` ไม่ใช่ `exec api`** เพราะอิมเมจของ API
> ตัด dependency ฝั่ง dev ออกหมดแล้วจึงไม่มี Prisma CLI ติดมาด้วย เซอร์วิสนี้
> อยู่หลัง compose profile คำสั่ง `up` จึงไม่สตาร์ทมันขึ้นมา

<details>
<summary><b>รันโดยไม่ใช้ Docker</b></summary>

```bash
# API — ต้องมี PostgreSQL 16 (pgvector ไม่บังคับ)
cd backend
cp .env.example .env    # ตั้งค่า DATABASE_URL และค่าลับต่าง ๆ
npm install
npx prisma migrate deploy && npm run db:seed
npm run start:dev       # → http://localhost:3000

# คอนโซล
cd ../web
npm install && npm run dev    # → http://localhost:5173 ต่อ /api ให้อัตโนมัติ

# มือถือ
cd ../mobile
flutter pub get
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:3000/api/v1
```

เอกสาร API แบบโต้ตอบอยู่ที่ `/api/docs` เมื่อ `NODE_ENV` ไม่ใช่ `production`
ซึ่ง compose ตั้งเป็น production ไว้เป็นค่าเริ่มต้น ถ้าต้องการใช้ให้ตั้ง
`NODE_ENV=development` ใน `.env`

</details>

### การลา

ประเภทการลาตามกฎหมายไทย การสะสมวันลาตามอายุงาน ลาครึ่งวันและลาเป็นชั่วโมง
พร้อมบัญชีวันลาที่ **กันวันของคำขอที่ยังไม่อนุมัติไว้ทันที** คำขอสองรายการ

### ลงเวลาทำงาน

ลงเวลาเข้า-ออกพร้อม geofence และการตรวจจับความผิดปกติ ตารางกะ การแก้ไขเวลา
และโอทีตามอัตราของ พ.ร.บ. คุ้มครองแรงงาน

**การลงเวลานอกพื้นที่จะถูกติดธง ไม่ใช่ถูกปฏิเสธ** พนักงานต้องพิสูจน์ได้เสมอว่า

## การตัดสินใจที่ควรรู้ไว้

**กฎทางธุรกิจเขียนเป็นฟังก์ชันบริสุทธิ์** การคำนวณวันลา การสรุปเวลาทำงาน
ภาษีไทย การให้คะแนน KPI และการตรวจแบบทดสอบ อยู่ในโฟลเดอร์ `domain/`
ที่ไม่แตะฐานข้อมูล ไม่ผูกกับเฟรมเวิร์ก และไม่มี I/O นี่คือเหตุผลที่เทสต์
ฝั่ง backend 245 ตัวรันจบในสิบวินาที — และที่คำถามว่า *"ทำไมถูกหัก 2.5 วัน"*
ตอบได้ด้วยการอ่านฟังก์ชันเดียว ไม่ต้องไล่ query

**เงินเดือนไม่ถูกหารตามจำนวนวันที่มีข้อมูลลงเวลา** พนักงานรายเดือนได้รับ
เต็มเดือน หักเฉพาะวันลาไม่รับค่าจ้างและวันขาดงานที่ *ระบุชัดเจน* เท่านั้น
วันที่ยังไม่ได้ปิดยอด เช่นวันในอนาคต หรือช่วงที่ยังทยอยติดตั้งระบบลงเวลา
ต้องไม่ทำให้เงินเดือนลดลง พลาดตรงนี้คือการจ่ายขาดแบบเงียบ ๆ
ซึ่งเป็นบั๊กเงินเดือนที่แย่ที่สุด

**บันทึกการใช้งานเขียนเพิ่มได้อย่างเดียวในระดับฐานข้อมูล** ทริกเกอร์จะโยน
exception ทันทีที่มีคำสั่ง `UPDATE` หรือ `DELETE` กับ `audit_logs` และ
`attendance_punches` บัญชีแอปพลิเคชันที่ถูกยึดจึงเพิ่มรายการได้ แต่แก้ไข
ประวัติไม่ได้

**บัญชีที่มีสิทธิ์สูงเข้าระบบด้วยรหัสผ่านอย่างเดียวไม่ได้** ใครที่อ่าน
เลขบัตรประชาชนได้ ทำเงินเดือนได้ หรือแจกสิทธิ์ได้ ต้องมีปัจจัยที่สอง
TOTP เขียนขึ้นเองและทดสอบกับชุด test vector ของ RFC 6238 โดยตรงแทนการ
พึ่ง dependency ภายนอก และรหัสหนึ่งตัวใช้ซ้ำไม่ได้แม้จะยังอยู่ในช่วงที่
ยังไม่หมดอายุ

**ไฟล์ที่อัปโหลดถูกสแกนก่อนถูกเก็บ** เรซูเม่มาจากหน้าสมัครงานสาธารณะ ซึ่งเป็น
input ที่เชื่อถือได้น้อยที่สุดของระบบ ไฟล์จึงถูกส่งไป clamd ก่อน มัลแวร์จึงไม่เคย
ถูกเขียนลงที่ไหนให้การแก้กฎในอนาคตเผลอเปิดเผยได้ และ**สแกนเนอร์ที่ไม่ทำงาน
ไม่เท่ากับผ่าน** — ต่อไม่ได้ หมดเวลา หรือตอบมาแบบที่อ่านไม่ออก ทั้งหมดทำให้ไฟล์
ถูกกักไว้และดาวน์โหลดไม่ได้

**เครื่องมือของผู้ช่วย HR ไม่รับพารามิเตอร์รหัสพนักงาน** ทุกตัวอ้างอิงตัวตน
จากผู้ใช้ที่ยืนยันตัวตนแล้วเท่านั้น จึงไม่มีช่องให้ prompt injection สั่งให้
ไปอ่านสลิปเงินเดือนของคนอื่น ต่อให้โมเดลถูกยึดทั้งหมด ขอบเขตความเสียหาย
ก็จำกัดอยู่แค่สิ่งที่ผู้ใช้คนนั้นเห็นได้อยู่แล้ว
ดู [ADR-0004](./docs/adr/0004-assistant-tool-scoping.md)

## ภาษาและการปรับใช้ต่างประเทศ

หน้าจอเป็นภาษาไทย และระบบเงินเดือนทำตามกฎไทย — ภาษีหัก ณ ที่จ่าย ประกันสังคม
และโอทีตาม พ.ร.บ. คุ้มครองแรงงาน แต่ *สถาปัตยกรรม* ไม่ได้ผูกกับประเทศไทย:
ชุดกฎภาษีเป็นข้อมูล (`THAI_TAX_RULES_2026`) ประเภทการลาเป็นค่าตั้งค่า และ
ตัวคูณโอทีเป็นการตั้งค่าระดับองค์กร การเพิ่มประเทศใหม่จึงหมายถึงการเพิ่ม
ชุดกฎและแปลภาษา ไม่ใช่การเขียนใหม่ทั้งระบบ
(ภาษาอังกฤษอยู่ใน [backlog](./docs/backlog.md) รหัส CW-016)

## สถานะปัจจุบัน

ใช้งานได้จริงและตรวจสอบครบตั้งแต่เข้าสู่ระบบจนถึงจ่ายเงินเดือน มี unit test
ฝั่ง backend 245 ตัว เว็บ 17 ตัว มือถือ 33 ตัว พร้อมชุดทดสอบ end-to-end
อีก 103 จุดตรวจที่ยิงผ่าน HTTP จริงใน CI และตรวจคอนโซลบนเบราว์เซอร์จริงกับ
API ที่รันอยู่

ระบบยืนยันตัวตนสองขั้นตอน การสแกนมัลแวร์ไฟล์อัปโหลด การจำกัดอัตราแบบใช้
ตัวนับร่วมกัน และการส่งอีเมล/push ทำครบแล้ว ส่วนที่เหลือติดตามได้ใน
[backlog](./docs/backlog.md) เรียงจาก P0

**ยังไม่พร้อมใช้งานจริงหากไม่ทำงานเพิ่ม** ก่อนนำไปคำนวณเงินเดือนจริง
กรุณาอ่าน [รายการช่องโหว่ใน docs/security.md](./docs/security.md#what-this-does-not-do)
สรุปสั้น ๆ: ยังไม่มีวิธีสร้างองค์กรใหม่โดยไม่ต้องโหลดข้อมูลตัวอย่าง ยังไม่มี
การส่งออก ภ.ง.ด.1 เอกสารที่ออกให้ยังไม่ถูก render เป็น PDF แอปพนักงานยัง
ลงทะเบียนรับ push ไม่ได้ และโค้ดนี้ยังไม่เคยผ่านการทดสอบเจาะระบบ

**กฎภาษีและประกันสังคมไทยในระบบนี้ยังไม่เคยผ่านการตรวจสอบจากผู้มีคุณวุฒิ**
เขียนขึ้นจากเอกสารที่เผยแพร่สาธารณะ และทดสอบกับตัวอย่างที่คำนวณด้วยมือ
ซึ่งพิสูจน์ได้เพียงว่าโค้ดคำนวณตรงกับที่ผู้เขียนเข้าใจ ไม่ได้พิสูจน์ว่า
ความเข้าใจนั้นถูกต้อง กรุณาตรวจตัวเลขกับของท่านเองก่อนใช้งานจริง หากท่าน
มีคุณวุฒิพอจะตรวจสอบได้ เชิญที่ [issue #36](https://github.com/SuruchBoss/Cwork/issues/36)

## เวอร์ชัน

การปล่อยเวอร์ชันจะถูก tag ไว้และบันทึกใน [CHANGELOG.md](./CHANGELOG.md)
หากต้องการบอกได้ว่ากำลังรันเวอร์ชันไหน ให้ติดตั้งจาก tag แทนที่จะใช้ `main`:

```bash
git clone --branch v0.1.0 https://github.com/SuruchBoss/Cwork.git
```

**ตอนนี้ยังเป็น 0.x การเปลี่ยนแปลงที่ทำให้ของเดิมพังยังเกิดขึ้นได้**
ทุกครั้งจะถูกบันทึกใน changelog พร้อมวิธีรับมือ แต่ยังไม่มี branch แบบ
long-term support และยังไม่รับประกันว่าการอัปเกรดจะราบรื่นจนกว่าจะถึง 1.0
migration เดินหน้าทางเดียว — สำรองฐานข้อมูลก่อนทุกครั้ง

1.0 หมายถึง schema และ API นิ่งพอจะให้สัญญานั้นได้ ซึ่งยังอีกไกล
และการแกล้งทำเป็นว่าถึงแล้วคือความผิดพลาดที่แพงกว่า

## โค้ดนี้ถูกเขียนขึ้นมาอย่างไร

**โค้ดใน repository นี้เขียนโดย AI agent** ที่ทำงานภายใต้การกำกับ ภายในเวลาไม่กี่วัน
หลาย commit เพิ่มโค้ดครั้งละหลายพันบรรทัด ซึ่งเห็นได้จาก `git log` อยู่แล้ว
และมันเปลี่ยนสิ่งที่ท่านควรตรวจก่อนจะเชื่อถือโค้ดนี้ จึงเขียนบอกไว้ตรงนี้
แทนที่จะปล่อยให้เดาเอาเอง

สิ่งที่**ไม่ได้**ถูกสร้างโดย AI: สถาปัตยกรรม แบบจำลองความปลอดภัย ลำดับความสำคัญ
และเหตุผลเบื้องหลังทั้งหมด — คนเป็นผู้ตัดสิน บันทึกไว้ตอนที่ตัดสิน และอ่านได้ที่
[spec.md § Agreed direction](./docs/spec.md#agreed-direction) กับ [ADR](./docs/adr/)
ส่วนตั๋วงานไหนที่ตั้งสมมติฐานไว้ผิด การแก้ความเข้าใจนั้นถูกบันทึกคู่กับสิ่งที่ทำจริง
ในตาราง Done ของ backlog — บันทึกนั้นคือสาระสำคัญ

สิ่งที่ตามมาเรื่องการตรวจทาน:

- ชุดทดสอบผ่านครบทุกชุดใน CI ทุกครั้งที่ push — backend 245 ตัว เว็บ 17 ตัว
  มือถือ 33 ตัว และ end-to-end อีก 103 จุดตรวจที่ยิงผ่าน HTTP จริง
- การตัดสินใจถูกบันทึกไว้ และย้อนดูเหตุผลได้
- **ยังไม่มีมนุษย์อิสระคนใดอ่านโค้ดครบทุกบรรทัด** การที่เทสต์ผ่านและการที่
  การออกแบบมีเหตุผลรองรับ ไม่ใช่สิ่งเดียวกับการถูกตรวจทาน โปรเจกต์นี้มีสองอย่างแรก
  แต่ยังไม่มีอย่างที่สาม

ประวัติ commit ไม่ได้ถูกเขียนใหม่ให้ดูเหมือนมนุษย์ทำ และจะไม่ทำ — การเขียนใหม่
ต่างหากคือความไม่ซื่อสัตย์ตัวจริง

คือกำแพงที่ตั้งขวางหน้าการแก้โค้ดบรรทัดเดียว ส่วน DCO ตอบคำถามเดียวกับที่
คนมักใช้ CLA ถาม ผลที่ตามมาซึ่งยอมรับแล้วคือสัญญาอนุญาตจะเปลี่ยนภายหลังไม่ได้จริง
เพราะต้องขอความยินยอมจากผู้ร่วมพัฒนาทุกคน — Apache-2.0 จึงเป็นคำตอบถาวร
